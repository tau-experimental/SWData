## Конечная цель проекта
Создание "пробивного" экспедиционного радиомодема/трекера для экстремальных приполярных КВ-трасс, условно "Москва-Командорские острова". Эту цель почти невозможно достичь, но нужно сделать всё возможное, чтобы хотя бы асимптотически приблизиться. Для работы должно хватать полевой антенны и мощности 20 ватт. Усилитель класса C или (предпочтительно) E.

## Сигналы, модуляция, предполагаемый протокол
0. Входной и выходной сигнал: пары I/Q 16 бит, частота сэмплирования 8кГц фиксированная, "сырая" полоса (до обработки) 300..2700 Гц. Считаем опорные генераторы стабильными как "типичный TCXO", но начальная настройка может быть с точностью +- 100 Гц (т.е. сигнал сначала надо найти)
1. Обязательное наличие предваряющего пилот-тона перед началом посылки (1..2 секунды, обсуждаемо). Пакет данных сопровождается передачей пилот-символов: на каждый интервал по N=10 символов (число обсуждаемо. Возможно, его стоит сделать настраиваемым, но уже на следующих этапах развития протокола) данных - M=1 пилотный, без информационной нагрузки, нужный для подстройки частоты; если фрагмент данных короче интервала (хвостовик пакета, K символов), тогда передача этого фрагмента завершется пилот-символом. То есть, всё поле данных передаётся так: M символов пилота - N символов данных - M символов пилота - ... - N символов данных - M символов пилота - (K<N) завершающих символов данных - M символов пилота, конец передачи. Естественно, что процедура сборки данных выкидывает все служебные символы, "склеивая" данные в единый массив.
2. Модуляция 2-MFSK (преамбула), 4-MFSK (данные), непрерывная фаза, символьная скорость 31.25. Набор тонов на данном этапе определён так: 
#define TONE_BASE	800.0f
#define TONE_STEP	31.25f
#define TONE(n)	((float)(TONE_BASE + (n)*TONE_STEP))
typedef enum { TONE_A, TONE_B, TONE_C, TONE_D } Tone_t; 
В передатчике эти энумы взаимоувязаны с конкретным значением частоты. Макросами можно изменить набор частот, но такая замена должна быть обоснованной: чем новые частоты "лучше" старых?
3. Два типа пакетов: DATA (20 байт данных + 6 байт избыточности КРС, всего 4 таких порции на пакт), ACK (аналогично, 4 порции по "8 байт данных + 6 байт избыточности КРС"). Механика различения типов DATA/ACK должна быть абсолютно надёжной. Перемежение работает по всему пакету данных.
4. Преамбула: не хуже MLS-31 (использование других последовательностей допустимо, если есть обоснование: какие выгоды по надёжности даёт такая замена?), передаётся с использованием TONE_A (символ -1) / TONE_D (символ +1)
5. Общая структура сигнала на данном этапе проектирования предполагается такой: пилот-тон -> преамбула -> пилот-символ -> тэг типа пакета (допустим, один символ: TONE_D кодирует "DATA", TONE_A кодирует "ACK") -> пилот-символ -> данные.

## Текущие наработки, состояние проекта, фокус работы, идеи.
1. Наработано и проверено некоторое количество решений:
	1. Утилиты для тестовых стендов (запись-чтение аудиофайлов для имитации канала), маленькая библиотечка для комплексной математики (типы cplx_f32, cplx_i32, cplx_i16), простейший табличный DDS MFSK модулятор (имитирующий работу передатчика путём записи сигнала в WAV). Есть скелетный вариант набора функций для FEC: свёрточное кодирование с "мягкими решениями", коды Рида-Соломона, перемежитель (интерливер), скрэмблер. Есть частично отлаженный симулятор зашумлённого радиоканала.
	2. На данном этапе нужно разработать соответствующие системы обнаружения сигнала, поиска преамбулы и синхронизации, устойчивые к флаттеру и прочим шумам.
2. Архитектурно задумка выглядит так:
	1. Блок децимации (8 кГц -> 1 кГц): целочисленный CIC-фильтр для RISC-V или какие-то иные варианты (чтобы не бороться с переполнениями, например).
	2. Блок поиска пилота: Реализация грубого поиска через FFT (64,128,256?) на частоте 1 кГц с определением начального сдвига частоты (+-100 Гц), всю полосу сдвигаем и центрируем вокруг нулевой ПЧ.
	3. Контур ЧАП (Частотной автоподстройки): Работает строго интервально — только на стартовом длинном пилоте и на пилотах-вставках. Он компенсирует исключительно термический дрейф генераторов базовой станции и трекера. Предел устойчивости к шумам должен получиться никак не хуже SNR = -6дБ в полосе 2500Гц, а если получится ещё ниже, то это просто замечательно. Чётко следуем правилам:
		1. Правило 1: Экстремальное демпфирование петли (Очень «тупой» контур).Поскольку мы боремся только с термическим дрейфом кварца (который плывет со скоростью долей Герца в секунду), коэффициент передачи петли ЧАП должен быть микроскопическим. Ложная шумовая вспышка на одном пилот-символе должна сдвигать частоту LO не более чем на 0.01–0.05 Гц. Контур должен сглаживать ошибку на интервале десятков секунд.
		2. Правило 2: Медианная фильтрация и отбраковка по амплитуде.Перед тем как скорректировать LO по пилот-символу, приемник должен проверить его абсолютную энергию P. Если P подозрительно мала (символ попал в глубокое авроральное замирание флаттера), этот замер частоты нацело выбрасывается, а частота LO удерживается старой.
		3. Правило 3: Ограничение шага (Hard Limiting).Величина единичной коррекции частоты LO между пакетами данных должна быть жестко ограничена сверху (например, не более +-1 Гц за один шаг подстройки), что полностью исключит катастрофический уход частоты из-за случайного мощного импульса помехи в эфире.
	4. Внутри блока данных: Частота LO фиксируется. Контур автоподстройки «спит».
	5. Борьба с флаттером: на уровне сигнала задачу решает некогерентный метод демодуляции (измерение энергии, а не фазы) и последующий помехоустойчивый FEC-декодер (Витерби) работающий с мягкими решениями, который исправит редкие символы, попавшие под аномально сильный ионосферный прыжок частоты, и интерливер, "размазывающий" сосредоточенные во времени помехи по всему пакету.

## Условия и ограничения
0. Вычислительное ядро: микроконтроллер 144МГц RISC-V RV32IMF, расширение M умеет только умножать (не делить), расширение F (single-precision) может умножать-делить-складывать, сравнивать и вычислять квадратный корень. 
Оперативная память: 64 килобайта на все нужды
Память программ: 127 кБ, причём работает так же быстро, как ОЗУ.
Кэш отсутствует.
1. Весь код должен быть написан на ANSI C, без использования сторонних библиотек (кроме стандартной библиотеки языка C и SPL для микроконтроллера) и представлен в виде конвейера функций, максимально изолированных друг от друга. Структуры данных, определения, прототипы - в соответствующих заголовочных файлах. Идеи из других проектов заимствовать можно и нужно, если это на пользу.
2. Приёмник и передатчик пишем сразу как будто для микроконтроллера, тестовый стенд - для ПК. Моделируемые алгоритмы максимально лаконичны, но для моделирующей системы ограничений нет.
3. Всю информацию о сигнале приёмник получает исключительно из самого сигнала, но при моделировании мы, конечно же, можем контролировать и сравнивать сигналы, состояния и всё что угодно.
4. На этапе отладки максимально используем возможности ПК: вывод в консоль, сохранение csv дампов состояния функций и сигналов для визуализации gnugplot (рендер в png).
5. Модель канала передачи сигнала: "передатчик" пишет I/Q сэмплы в WAV PCM 16 bit Signed, затем по этому файлу проходит настраиваемый симулятор помеховой обстановки и свой результат пишет в другой файл, который уже считывается приёмником. Тесты на чистом сигнале, на сигнале средней зашумлённости, на очень сильно испорченном сигнале. Переходить к следующему этапу, не отладив предыдущий, запрещается.
6. Не писать новый код, не убедившись в том, что он вписывается в существующую систему API и вообще в концепцию, не ломая функционал других узлов (например, нельзя просто менять или заново писать передатчик, оставив приёмник "как есть", если переделка приведёт к несовместимости -- сначала надо убедиться в том, что имеющихся функций не хватает и нужно их дополнить чем-то полезным).
